# Критическая проверка перед пилотом — 06.11.2026

Проверена ветка `codex/seo-system-foundation` относительно pinned upstream `738e86a84a55c44ef9093b6631943bef8a4738e0`, исходного ТЗ и пожеланий о полном цикле, Google Drive, Labrika, Яндексе и GSC. Предыдущие 59 тестов и 144 сохранённых файла подтверждали структурный перенос и ряд gates, но не содержательную полноту. Вывод прежнего status «адаптация завершена, пора в пилот» был слишком широким. После исправлений допустим ограниченный пилот с ручным предметным ревью каждого продукта; автономная SEO-система с подключёнными сервисами не развёрнута.

## Внешние источники и актуальность

Manifest path теперь ограничен input bundle. Нормализатор не исполняет содержимое HTML/CSV/JSON; XLSX читается без формул/macros/external links, с byte/expanded-size/row limits. Prompt injection в тексте остаётся риском ручного чтения Codex: AGENTS и permissions требуют трактовать внешние команды как данные. Совпадение SHA и claims не доказывает честность первичного сервиса, полноту экспорта или правильность ручной нормализации. Разработка не является полным security audit.

C01–C17 в instructions/currentness.md содержат первичные ссылки. При этой проверке повторно сверены Google AI guidance, FAQ retirement, disavow и отдельно устаревшие HowTo/sitelinks promises исходного launch. Правила word count/density/title lengths, ссылочных квот, ROI и индексации оставлены контекстными и доказательными. Публичный Labrika catalogue не превращён в доступ ко всем reports/API; AI mentions/citations/positions отделены, теханализ не ограничивает предполагаемые возможности Labrika.

Фактические доступы из предшествующих read probes: Drive search/read/native Sheets export подтверждены в этой сессии; CLI storage/write adapter нет. GSC active connection отсутствует; Yandex generic connection не подтверждает counter/host read. Labrika usable tool/UI session не подтверждены. В этой проверке подключений и платных запусков не создавалось. Детали и границы — docs/access-verification.md.

## Доказательства и границы готовности

86 unittest tests проходят, включая 27 новых pilot-review regressions. `test_each_workflow_really_submits_and_persists_all_nodes` оборачивает настоящий submit без подмены его результата, проверяет число вызовов по DAG, продукты и completed events в SQLite для всех 11 workflows и agency-cycle. Другие тесты проверяют artifact IDs между узлами, immutable sources/products, inherited partial, claims, release evidence, fresh post-checks, comparisons и конкретные негативные примеры выше. Это подтверждает исполнение координации и выбранных gates, а не только валидацию JSON fixture.

`render_playbook.py --check`, `check_playbook.py`, `check_repository.py` и `git diff --check` — дополнительные проверки документации, pinned hashes, ссылок/схем/DAG и ограниченных repository patterns. Они не являются проверкой качества всей библиотеки. Version 0.3 отличает новые contracts от старых результатов.

Блокера на чтение инструкций и локальное прохождение ограниченного пилота нет. До клиентской приёмки нужно выбрать реальный сайт/цель и разрешённый существующий dataset, проверить его scope/date/normalization, выбрать минимальный workflow и вручную принять каждый предметный output. Не включать недоступные модули как completed; вести partial/blocked. Без реального release evidence Execute остаётся prepared; без свежих checks — unverified; без закрытых подходящих окон — awaiting measurement. Нужды запрашивать все аккаунты заранее нет.

Остаются: ручной substantive QA большинства ролей, сравнительно узкие typed contracts, отдельная модель календарных кварталов, внешние storage/API adapters, failed-submit audit ledger, multi-worker locks/leases, scheduler/deployment/monitoring и реальный end-to-end клиентский кейс. Не публиковались изменения, не менялись main/production, не удалялись прежние файлы.
