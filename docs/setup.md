# Установка и первый реальный запуск

1. Выполнить `uv sync --frozen` из репозитория. Зависимости: jsonschema и openpyxl; сеть нужна только для установки отсутствующих пакетов. Для среды с read-only домашним каталогом используйте `UV_CACHE_DIR=/tmp/spinoff-uv-cache uv sync --frozen`. Локальный код не требует API-токенов.
2. Выбрать пилотный сайт, домены/поддомены, цель, регион, язык, engines/device и фактическую текущую ревизию сайта. Демо-профиль — только образец формата; не переносить его значения в клиентский проект автоматически.
3. Создать приватный workspace вне Git либо в игнорируемом workspace/. Для устойчивой работы нужен сохраняемый локальный диск и резервное копирование. Этот environment пока не подтверждён как постоянное хранилище.
4. Создать profile.json по seo_system/schemas/project.json. Drive ID пока null, monthly_capacity_hours при неизвестности null. Заполнить реальные данные, не секреты. `site_revision` может быть commit/CMS revision либо явный идентификатор снимка; он должен совпадать с источником.
5. Получить разрешённую готовую выгрузку, сохранить raw без изменения байтов. Подготовить source-manifest.json с SHA-256 (`sha256sum <file>`), исходной датой анализа, датой получения, количеством строк и честным coverage. `file` разрешается относительно manifest. Не заменять старую дату текущей ради прохождения gate.
6. Для CSV/XLSX выбрать фактические поля. Сначала можно выполнить `seo inspect-import --file <path> --format xlsx`, затем при необходимости `--sheet '<имя>'` для первой строки. Пример mapping: `{"url":"Адрес страницы","status_code":"HTTP-код","title":"Title"}`. Эти названия условные, не подтверждённые имена колонок Labrika. Для XLSX указать реальный sheet. Таблица рекомендаций, задач или регламент без URL/HTTP-кодов не подходит для этого pages-среза: нужен другой источник или будущий тип dataset, не выдуманный столбец.
7. Выполнить preflight и run как в README с путями пилота. Посмотреть coverage, факты и evidence до подготовки изменений. Run с ошибкой возвращает exit code 2 и не считается принятым.

Для прямого подключения сервисов сначала определить конкретный аккаунт/property, модуль и способ доступа. Сохранить доказательства в templates/source-capability.json в приватном проекте. Секреты выдаёт пользователь через хранилище среды; не писать значения в профиль, Git, Drive или отчёт. Название источника `labrika` в manifest — provenance, не подтверждение API.

Доступные инструменты текущей сессии уже умеют читать выбранные Drive-файлы и экспортировать native Sheets в XLSX; это проверено read-only. Ими можно получить разрешённый конкретный источник и материализовать в приватный workspace с provenance. CLI не наследует OAuth этих инструментов. Ни Google OAuth client ID/secret, ни активное общее подключение Яндекса сами по себе не доказывают доступ к GSC, счётчику Метрики или Вебмастеру. Актуальный протокол — docs/access-verification.md.

Drive подключается следующим этапом: согласованная тестовая папка → разрешённый write/read smoke test → fileId/version/checksum → идемпотентный outbox/reconciliation → проверка восстановления. До этого локальный пакет нельзя называть сохранённым в Drive. Не менять sharing автоматически.
