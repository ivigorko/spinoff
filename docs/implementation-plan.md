# Состояние внедрения и последовательность расширения

Адаптация MASTER-PLAN.md с исправлениями исходного ТЗ. Цель — управляемый цикл, а не количество агентов.

1. Сохранить upstream, сверить весь inventory и методические правила. Выполнено: preserved snapshot и source map, 75 предметных процедур, 12 leads, 17 team/general instructions, 11 исходных workflows, onboarding, base/QA/tools/templates.
2. Связать процедуры с контрактами и scoped artifacts. Выполнено: каталоги, role/team selectors и локальный coordinator с frozen DAG, source/product registry, dependency/partial/QA/evidence gates. Предметный анализ выполняет Codex.
3. Проверить цепочки на синтетических fixtures, включая невозможность фиктивного release/verification/measurement. Проверки фиксируются в docs/status.md; они не доказывают эффективность SEO и качество любого будущего ручного анализа.
4. Провести реальный ограниченный пилот по выбранному сайту и существующим пригодным источникам. Пилот не выбирался автоматически; готовый регламент не подменяет измерительный dataset.
5. Подключать по одному реально полезному direct/storage adapter после подтверждения scope, формата, permissions и лимитов. Сейчас Drive session read/export проверен; автономного write/storage adapter нет. GSC/Метрика/Вебмастер/Labrika CLI adapters не имитируются.
6. По конкретному поручению пройти первое prepared change → фактический разрешённый release → fresh verification → измерение по закрытому окну. Координатор способен принимать и проверять записи этих этапов, но не выполняет deployment и не гарантирует причинный рост.
7. Только при необходимости расширять на multi-worker DB/leases/fencing и реально проверенное расписание; текущая SQLite — один локальный писатель.

Отсутствие всех API не мешает полноценному применению инструкций Codex с разрешёнными готовыми данными. Оно ограничивает автоматизацию получения/доставки, что должно оставаться видно пользователю.
