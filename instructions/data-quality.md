# Качество

## Общие требования

Политика возраста едина: seo_system/config/freshness.json. Новая загрузка не омолаживает источник. Будущее время и неправильный порядок дат отвергаются. Для текущих технических наблюдений site_revision профиля и источника должны совпадать; после релиза нужна новая проверка затронутых URL, даже если старый crawl ещё моложе 14 дней.

Критические проверки: верный project/host/market, checksum, типы и гранулярность данных, chronology/freshness/revision, разрешимые evidence, отсутствие противоречий, передача точных artifact IDs и соответствие выбранному contract. Проверки уникальности зависят от grain: для pages — URL, для позиций — query/engine/region/device/date, для дневных метрик — date и scope. Нельзя компенсировать провал критической проверки средней оценкой качества. Неполноту раскрывать явно; неизвестное не заменять нулём.

## Старый технический CLI

Только `seo run --workflow technical` и его legacy alias `seo run --workflow go` применяют три автоматических правила: HTTP >= 400, пустой title и пустой h1 на HTTP 200. Они дают наблюдения и задачи ревью. HTTP 404 может быть намеренным; автоматического требования восстановить любой URL нет. Индексация, canonical, CWV и orphan pages по этим полям не выводятся. Нулевое число находок не означает здоровый сайт.

Выход именно этого технического CLI всегда partial, включая legacy alias go: это ограниченный pages-срез, а не полный SEO-аудит. Missing fields отражаются в coverage; не генерировать по ним находки. Для расширения этих правил нужны проверенные поля, acceptance tests и ограничения выводов. Разговорное поручение «go/full audit» маршрутизируется по AGENTS.md в процесс full-seo-audit, а не в этот alias.

## Процессные и аналитические запуски

`seo process ...` использует выбранные workflows/roles, их зависимости, предметные sections и evidence contracts. На эти процессы ограничение «только три правила» не распространяется. Результат может быть completed в явно выбранном scope после всех обязательных gates либо partial/blocked при неполных данных или проверках. Ни completed, ни наличие заполненных sections не заменяют предметного ревью; уровни автоматических guards и ручного QA описаны в docs/pilot-critical-review.md.

Периоды сравнивают с одинаковыми definitions/property/timezone/filters и закрытыми окнами. По умолчанию `equal_duration` сохраняет требование равной длины. Явный `calendar_month` допускает различную длину только для двух полных календарных месяцев и при зарегистрированных analytics evidence о полном непрерывном наблюдении и дневных суммах. Первое число, последний день, границы наблюдения в timezone, отсутствие известных gaps, уникальность/полнота daily rows и сверка total обязательны. Наличие всех дат или нулевых строк само по себе не доказывает работающий весь месяц счётчик. Подробный контракт: docs/calendar-comparison.md.

Достижения целей не означают пациентов; суммы разных целей не являются уникальными обращениями. Пустая позиция не становится нулём, изменение числа запросов в топе не является изменением трафика или взвешенной видимости. Даже полное покрытие календарных месяцев не доказывает причинный SEO-эффект или сезонную сопоставимость.

## Защита данных

Секреты и клиентские данные не должны попадать в Git. scripts/check_repository.py проверяет индекс и рабочее дерево управляемых Git-файлов на характерные секреты/запрещённые пути; это вспомогательный барьер, не полная DLP-проверка. Сырые выгрузки и персональные данные должны оставаться вне репозитория.
