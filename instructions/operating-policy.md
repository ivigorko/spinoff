## Пять файлов и сдача карточки

Папка 01_Карточка содержит пять отдельных файлов:

1. Профиль: компания, сайт, ниша/модель, текущий трафик с источником/датой либо unknown, платформа, история SEO, ограничения.
2. Сайт и доступы: конкретные сервисы/properties/права и фактическая проверка разрешённого входа; недоступное перечислено. Метрика, Вебмастер, Яндекс Бизнес, 2ГИС, сайт, SEO Reports, хостинг на чтение — по чек-листу; дополнительно Labrika/GSC по реальной задаче. Пароли и строки credentials не читаются в вывод и не сохраняются в карточке.
3. Конкуренты: 3–5 поисковых конкурентов с URL и основанием выбора; кандидаты не называются доказанными лидерами без замера. До исследования использовать уже подтверждённые данные, не проводить запрещённое исследование для заполнения карточки.
4. Цели: три цели, числовой успех за 90 дней, приоритетные запросы и бюджет часов. Неизвестное явно перечисляется и передаётся Игорю, не выдумывается ради закрытия gate.
5. Голос бренда: тон, стоп-слова, кто пишет, объём по задаче.

Сдача Нине: карточка, таблица задач, собственный чат проекта, строка «Мои Проекты», ограничения. Schema profile — индекс/версия контекста, не замена пяти файлов. Технический `completed` означает проверенный work-product, а не «Выполнено» в рабочей таблице и не настоящую приёмку Нины. При неполном комплекте сохраняется partial/блокер; следующая фаза не начинается автоматически.

## Порядок фаз и переходов

| Фаза | Необходимый переход | Работа и сдача |
|---|---|---|
| Онбординг | Действующая команда Игоря в её точном объёме | Пять файлов, доступы/ограничения, таблица/чат/реестр; настоящая приёмка Нины |
| Исследование | Карточка принята Ниной + команда Игоря на этот этап | Рынок и алгоритмы → конкуренты → семантика/Wordstat и снимок выдачи; 02_Исследование; приёмка Нины |
| Аудит | Исследование принято Ниной + команда Игоря | Технический обход первым; затем независимые заказанные контент/ссылки/GEO/локальное/магазин. Сводка, снимок «до», задачи, неизвестные; Нина закрывает аудит без открытых заказанных блокеров |
| Стратегия | Аудит принят Ниной + действующая команда | Стратегия, матрица эффект × трудозатраты 1–5 с основаниями/unknowns, план 90 дней недельными спринтами; приёмка Нины, утверждение Игоря |
| Исполнение | Утверждение стратегии/строк и команда «делай» — разные факты | Только выбранные разрешённые задачи; материал/ТЗ, baseline, tests, rollback, сдача Нине |
| Проверка/измерение | Реальный разрешённый релиз, самопроверка и вторая проверка Нины | Свежие expected/actual проверки, затем закрытое сопоставимое окно; без релиза/данных нет фиктивного эффекта |
| Отчёт/пересмотр | Фактическая работа и её приёмка; действующий объём поручения | Нина проверяет отчёт, передаёт Игорю на «ок»; клиенту только по принятому маршруту. Пересмотр возвращает к стратегии |

Не требуется новая команда на каждую независимую подзадачу, если она уже однозначно входит в действующее поручение. Но утверждение не равно запуску, а разрешение на одну фазу не переносится молча на следующую. Внеплановые/срочные задачи и снятие явного запрета — по отдельной команде Игоря. Свежий отчёт младше 30 дней по тому же вопросу сначала переиспользуется после проверки scope/полноты; это не отменяет более строгий freshness конкретных verification/measurement sources.

Внутри разрешённого этапа независимые задачи могут выполняться одновременно. Это правило порядка работ, не команда запускать subagents и не заявление об общей очереди. Зависимости и явные ограничения сохраняются; technical crawl не обходит непринятое исследование. `role:`, `team:`, специальный workflow, CLI importer, загрузка через будущий адаптер и новый workspace не являются исключениями.

## Приёмка и публикация — разные факты

Самопроверка и оценка качества 1–5 нужны; ниже 3 результат возвращается. Оценка ≥3 не закрывает критический провал, missing facts или незаказанное направление. Source/subject QA репозитория остаётся обязательным. Настоящая приёмка — фактическое решение Нины о конкретной версии материалов после их проверки. Её нельзя создать полем `reviewer=nina`, машинным QA или отдельным role-run.

Без выкладки задача становится «Выполнено» после приёмки Ниной. При выкладке — после самопроверки и второй проверки Нины. Тексты публикует/корректирует Слава после проверки Нины без дополнительного «ок» Игоря по общему регламенту; ссылка проходит через Нину к Игорю. Другие изменения сайта требуют конкретного «ок» Игоря в чате и статусом. Отчёты клиенту, внешние сообщения, оплаты/размещения и расходы требуют установленного отдельного scope/«ок». Явный более узкий запрет пользователя в конкретном проекте сильнее общего маршрута публикации. Код ничего не публикует и не отправляет.

Рабочие таблицы: исполнитель «Игорь»; функции остаются функциями. Статусы ровно: «На утверждении», «Утверждено, ждёт запуска», «В работе», «На проверке», «Блокер», «Выполнено», «Отложено», «Отменено». Технические состояния CLI не записываются вместо них. Нина ставит/принимает задачи и ведёт Оперативку; ПМ не заменяет её приёмку. Клиентские тексты — через Игоря. Самовольные сроки реакции 2/4/2 часа не вводятся; предложения сроков в источнике остаются предложениями.

## Что исполняет код

`seo_system/governance.py` задаёт общий phase gate для start/submit, source registration/optional skip, legacy execute и readiness. Contract4 проверяется на каждой мутации; старые продукты остаются историческими и не превращаются в принятую фазу. Фаза выводится из канонической роли, не из пользовательского поля phase в JSON. Code QA/dependencies/freshness/hash/subject guards сохранены.

Для client run нужны проверенные записи отдельной команды Игоря и настоящей приёмки предыдущего этапа Ниной. Приёмка связана с project/profile hash, run/artifact/hash и конкретными пятью файлами/ссылками карточки. Для исследования нужны содержательные market/algorithms/competitors/SERP/clusters outputs, а не один заполненный market JSON. Частичный продукт не закрывает фазу. Утверждение стратегии связано с тем же bundle, но не заменяет запуск исполнения. Явный hold не снимается общей командой: требуется отдельная команда с подтверждённым снятием именно этого запрета. Readiness не скрывает этот блокер.

Синтетический режим обходит внешнюю приёмку только для reserved example hosts, явно отмечен и не становится клиентским результатом. Legacy technical demo дополнительно требует project_id `synthetic-*`; произвольный реальный домен не включается этим флагом. Чистые функции парсинга/расчёта не являются защищённой очередью исполнения или sandbox для произвольного пользовательского Python.

## Что пока отсутствует и как не имитировать это

Нет доверенного reader реальных решений Нины/Игоря, общей очереди, coordinator identity authentication или Drive adapter/reconciliation. Поэтому CLI не имеет команды «approve»/импорта произвольного JSON решения: без проверенного внешнего источника клиентские gates закрыты. `VerifiedRead` — интерфейс доверенного адаптера, не доказательство личности. Будущий адаптер обязан сам проверить фактического автора/полномочия, проект, решение, версии файлов, явный start/hold и подлинный источник; нельзя создавать VerifiedRead из raw документов, профиля или QA. Тестовый reader в tests — фикция, не подключение к Нине.

Исполнитель сейчас обязан вручную прочитать актуальные документы/поручение, проверить очередь и владельца, подготовить комплект в разрешённом этапе и передать его Нине по реально разрешённому каналу. Без действительного подтверждения не продолжать. Эта ручная дисциплина не разрешает обходить закрытый CLI через роль, другой каталог или внешний upload. Нельзя обещать автоматическую синхронизацию, многопользовательские locks, приёмку или доставку; local SQLite — один писатель в одном workspace. Человек с правом менять код/БД может подделать локальное состояние: это не security boundary против такого оператора.
